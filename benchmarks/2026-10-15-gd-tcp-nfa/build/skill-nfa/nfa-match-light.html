Why a set of states

An NFA can be in several states at once. The matcher does not guess a path and back up when the guess is wrong. It carries every possible path forward together, as one set. Each symbol touches each state and edge at most once, so the time is O(n·m) for n states and m input symbols. Here that is 12 states and 5 symbols.

Most regex engines in standard libraries (JavaScript, Python re, Java, PCRE) backtrack instead. They try one path at a time. On some patterns, for example (a*)*b against a long run of a, that takes exponential time. RE2, Go's regexp and Rust's regex crate promise linear time. They use this set simulation, or automata built from it, and so they do not support backreferences.

From the NFA to a DFA

Each distinct set is one state of a DFA (the subset construction). This run meets 5 distinct sets: {0}, {1,2,3,4,5,9,10}, {3,4,5,6,8,9,10}, {3,4,5,7,8,9,10}, {11}. A full subset construction over the alphabet {a, b, c, d} also finds 5 sets, plus the empty set where every path has died. A DFA does one table lookup per symbol, but on some regexes it needs exponentially many states, so engines often build it lazily, one set at a time.

What the figure leaves out

  • The whole input must match, as with ^a(b|c)*d$. To find a match anywhere in a text, the matcher adds state 0 back into the set before each symbol.
  • Capture groups. A Pike VM, a variant of this simulation, gives each state in the set the positions where its groups started.
  • Real engines do not store the states that have only ε edges (1, 2, 3, 8 and 9 here). They keep only the states that read a symbol, plus the accept state. The figure keeps them all, as the textbook construction does.
